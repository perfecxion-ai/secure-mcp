# Browser acceptance with Keycloak

Run `npm ci`, `npm run build`, then `npm run test:keycloak` on Linux with Docker and Node 24. The lab takes several minutes because it waits for the real JWKS cooldown and access-token expiry. An optional argument to `verify.mjs` saves a bounded JSON report with image digests, browser version, and runtime module hashes.

The lab creates a disposable PostgreSQL database, starts Keycloak in production mode with HTTPS, launches an actual headless Chromium browser, and puts the MCP resource behind NGINX TLS. Host listeners bind to loopback. Images are digest-pinned in the script. Fixture passwords and signing material are generated per run, kept in private files, and removed with the containers on normal completion or test failure. Browser trust is pinned to the ephemeral certificate's public key; Node adds the fixture certificate to its normal trust store and keeps TLS verification enabled. Chromium runs without its inner sandbox inside the disposable container because this lab only visits its own issuer and callback; it is not a browser-isolation example. Do not use real accounts or expose its debugging port.

The browser submits an incorrect password, then the correct one, and accepts consent. The native-client flow uses an exact loopback redirect, S256 PKCE, state and issuer binding, and a verified ID-token nonce. Access tokens use the RFC 9068 header type, explicit resource audience, subject, short lifetime, and explicit scopes. Both MCP protocol versions read an approved document and deny traversal. A second client has policy scope only. The lab also tests ID-token rejection, real key rotation and refresh cooldown, fresh-cache versus cold-cache behavior during issuer shutdown, issuer restart, logout/refresh failure, natural JWT expiry, and authorization-code replay.

The imported realm deliberately defines the `basic` scope's subject mapper as well as the two application scopes. Omitting the subject mapper produced a token that the resource server correctly rejected. Keycloak's current login theme uses `input-error-username` and `kc-oauth`; earlier fixture selectors were updated before recording the passing result. Consent can be remembered, so subsequent logins may return directly to the callback.

This establishes a local integration with an independent maintained provider, not acceptance of your organization's login policy. MFA, federation, recovery, device enrollment, production certificates, and your own issuer outages remain operator validation tasks. The five-minute stale-cache transition and key removal are additionally covered by the deterministic HTTP-backed identity tests; this browser lab waits for real cooldown and expiry but does not wait for stale-cache expiry.
